# Contributing to SatDeed

SatDeed is a draft standard. At this stage, finding something wrong with it is
worth more than adding to it.

## What is most useful right now

**1. A second implementation.** In TypeScript, Rust, Go, anything. Written
from [`spec/SPECIFICATION.md`](spec/SPECIFICATION.md) alone, without reading
the Python, reproducing every record hash, identifier, commitment and Merkle
root in `examples/`.

This is the exit criterion for Phase 1 and Phase 2 of the roadmap, and it is
the only reliable test for ambiguity in a specification. Any place where your
implementation disagrees with the published values is a specification bug,
not an implementation bug, until proven otherwise. Please open an issue for
each disagreement.

**2. Attacks on the construction.** Particularly on the Merkle rules, the
commitment schemes, the identifier derivation and the anchor payload. If you
can produce two distinct inputs that verify against the same commitment, or
an inclusion proof for a record that was never in a batch, that is the most
valuable issue this repository can receive.

**3. Arguments that the whole approach is wrong.** The design rationale makes
a specific claim, that an anchor makes a registry's retroactive revision
detectable. If that claim does not hold, or if existing work already delivers
it, the project should know. Section 2 of the rationale names the closest
prior art and the case for simply using it instead.

**4. Legal analysis.** Whether anchored commitments carry evidentiary weight
in any particular jurisdiction is entirely unexplored and matters more than
any remaining engineering.

## What is less useful right now

Features. The specification already has more surface than it has
implementations, and v0.1 should get smaller before it gets larger.

## Ground rules

- The specification and the reference implementation must never disagree. A
  change to one requires a change to the other in the same pull request.
- Every value in `examples/` is generated by
  `reference/tools/generate_examples.py`. Never hand edit an example file.
  Change the generator and regenerate.
- New behaviour needs a test. New defences against a specific attack need a
  test that fails without the defence.
- Tests must pass with no third party dependencies. The reference library is
  deliberately dependency free so that it can be read and checked by anyone.

## Running things

```bash
python3 -m pytest reference/tests -q
python3 reference/tools/generate_examples.py
git diff --exit-code examples/   # regeneration must be deterministic
```

## Writing style

Prose in this repository uses commas rather than dashes.

Be concrete about limits. The standard's main virtue is that it states what it
cannot do, and documentation that overclaims undoes that.

## Security issues

Open a private security advisory rather than a public issue.
